TRMC, and is a flat array really faster than our cons list?

Two questions about wok's built-in list [a] = Cons head tail / Nil. First: what TRMC actually does. Second: whether LuaJIT-style flat arrays beat cons lists, and what that means for a reference-counted language with no compacting GC.

1 · Why naive map / chars piles up stack

The recursive call sits inside the Cons, so it is not in tail position. The machine must remember "wrap what comes back in Cons (f x) _" before it can recurse — one remembered frame per element.

map f xs = case xs of
  Nil        -> Nil
  Cons x rs  -> Cons (f x) (map f rs)   -- recursive call is an ARGUMENT, not the tail
map f [10,20,30]remember: Cons 11 _
↓ recurse
map f [20,30]remember: Cons 21 _
↓ recurse
map f [30]remember: Cons 31 _
↓ recurse
map f [] = Nilnow unwind, building cons cells

fig 1 — N elements means N stacked frames. Long lists overflow the stack.

2 · What TRMC does: build forward through a "hole"

Tail Recursion Modulo Cons rewrites the function to allocate each Cons before recursing, leaving its tail field as an empty hole. It keeps a pointer to that hole, fills it on the next step, and tail-calls — so the recursion becomes a flat loop. The one-hole context Cons (f x) _ becomes a mutable pointer instead of a stacked frame.

3 · Why TRMC wins (the part that was missing)

Picture building a list like coupling train cars. The naive way, you can't attach a car until every car behind it is built — so you stand there holding the whole half-finished train. That "holding" is the stack, and it grows with every element. TRMC lays the first car down, leaves the rear coupling open (the hole), and snaps each new car onto the open coupling as it goes. You only ever hold the latest coupling. Same train — but your arms stay empty.

The superiority only becomes obvious when you compare it to what people actually do when naive recursion overflows: build the list backwards into an accumulator, then reverse it at the end. That is stack-safe — but it walks the data twice and allocates a whole throwaway reversed list. TRMC is the only choice that is good on every axis at once:

on a long listnaive recursionbuild-and-reverse (the usual fix)TRMC

The superiority in one line: you write map the obvious way, and TRMC makes it stack-safe, single-pass, and in natural order — no rewrite, no second pass, no scratch list. And because it builds through a hole pointer, it lines up exactly with the reuse wok already has: over a list you uniquely own, a purely functional map then runs with zero allocation and constant stack — the speed of a hand-written C loop, from ordinary functional code.
Concrete: map (+1) over 10,000,000 items — naive recursion crashes with a stack overflow; build-and-reverse survives but takes 20,000,000 steps and allocates a 10M-cell scratch list; TRMC takes 10,000,000 steps once, in order, in constant stack.

4 · The catch that decides foldChars

TRMC's whole win is on one axis — stack depth, output order, and enabling in-place reuse. There is a separate axis it deliberately does not touch:

TRMC removes stack depth, not allocations. It still builds N fresh Cons cells — one Cons (f x) □ per element. It changes how the list is built (a forward loop), never how many cells exist.

Allocations are only avoided by reuse (Perceus, which wok already has): when you transform a list you uniquely own, each consumed input cell is handed straight to the next output cell — net zero allocation. But that needs an input list to cannibalize. Building a list from non-list input — a string into a char list — has nothing to reuse.

reuse applies

map f uniqueList

TRMC (O(1) stack) + reuse (0 alloc). The best case. Input cells become output cells.

reuse cannot apply

chars s (string → list)

No input cells exist to reuse. N allocations are unavoidable — TRMC or not.

So for foldChars: the only ways to avoid the throwaway char list are (a) don't build it — the dedicated fold frame — or (b) deforestation/fusion, a compile-time rewrite that an interpreter can't do. Optimizing [] does not compete with the frame. They are orthogonal.

5 · Cons cell vs flat array, in memory

This is the LuaJIT question. A cons list is N separate cells chained by pointers; a flat array is one contiguous block. The difference is mechanical, not a matter of taste.

wok cons list

24 bytes / element, scattered

cell @0x A: [hdr|11|•]---+
                          |
cell @0x F: [hdr|21|•]<--+ ---+
                              |
cell @0x3: [hdr|31|Nil]<------+

8B header + head slot + tail pointer. Traversal chases pointers to wherever malloc put each cell.

flat array (LuaJIT table / wok Array)

8 bytes / element, contiguous

[ 11 | 21 | 31 | .. ] one block
  ↑ index i = base + i*8 (O(1))
  ↑ 8 elements per 64B cache line

One allocation, no per-element header, prefetcher-friendly linear scan.

6 · Is the array actually faster? Yes — with caveats

prependO(n) (shift/copy)O(1)
structural sharingcopy neededfree (share the tail)
pattern match head/tailawkwardnatural

For bulk and indexed work the array wins decisively, and the empirical literature backs this even where lists "should" win (insertion that requires a search first). The advantage shrinks or reverses for small N, prepend-heavy code, and persistent/shared structures — where cons lists keep their classic strengths.

Sharper for wok specifically: wok is reference-counted with no compacting/copying GC. A cons cell is allocated once and never relocated, so a long-lived list's cells stay wherever they landed — maximally scattered. Copying GCs (OCaml, Java) can re-colocate survivors onto shared cache lines and partially heal this; wok cannot. So wok's cons lists are more cache-hostile than the ML/JVM baseline — except when bump-allocated together in one arena (Region R1), which lays them out contiguously and recovers much of the locality.
The point: wok already has the flat option — Array a. The right answer is not to reshape [] into an array (uniform polymorphism forecloses it, the same wall that stopped Array Slice D), but to keep both: Array for bulk / indexed / append, [] for prepend / sharing / pattern-matching. The one cons-list improvement worth its own future slice is TRMC — the producer half of the Koka story wok is missing. And in today's tree-walking interpreter, per-element dispatch overhead dwarfs cache effects anyway: the array's locality win is real but mostly cashes in at the codegen endpoint.

7 · Can we fuse list + array into one type?

You can — what you are describing already has names. A linked chain of small flat blocks is an unrolled list (constant block size) or a VList (geometrically growing blocks). TRMC builds either one's spine fine: fill a block's slots, and when it is full the hole jumps to a freshly linked block. The build path gets great locality and few allocations. The question is what it costs on every other path.

structureindexprependsharingtraversal localityhead/tail match
cons list + TRMCO(n)O(1)free, per-cellpoor (scattered)trivial
unrolled / chunked listO(n/K)O(1) amortizedblock-granulargood (within block)needs an offset
growable vector (Array)O(1)O(n)copybestawkward
RRB-tree (do-it-all)O(log n)O(log n)freegoodO(log n)

No row is all-green. The unrolled list buys locality by making head/tail decomposition carry an offset — every list value becomes (block, offset) instead of one pointer — and by coarsening sharing to whole blocks. The RRB-tree is the genuine "do it all" (Scala's Vector, Clojure), but at an O(log n) factor on everything and a large build — a third type, not a replacement for either existing one.

Why chunking the list is wrong for wok specifically: wok frees by reference counting, with no compacting GC. A cons cell is freed the instant its last owner drops it — consuming a list reclaims it element-by-element, promptly, and FBIP reuse recycles it. A chunk can only be freed once all K of its elements are dead and no tail-view points into it; holding the tail of a list pins the whole head block, including elements you already consumed. Chunking trades Perceus's prompt, precise reclamation for coarse, block-granular reclamation, and weakens in-place reuse. That is fine on the JVM (Clojure, Scala — a tracing GC sweeps anyway); under reference counting it is a regression.

8 · 1.5x, 2x, or constant block?

This is really two questions for two different structures, and the answer flips between them:

copy-on-grow buffer (a vector)

Geometric is mandatory

A single buffer you reallocate-and-copy must grow by a constant factor, or total copy work is O(n²). The only real choice is the factor.

linked blocks (a chunked list)

Constant block size

You never copy existing blocks — you link a new one — so there is nothing to amortize. A fixed K tuned to a cache line (~8–16 for 8-byte elements) is simplest and best. Geometric blocks (a VList) only buy O(1)-average indexing, which a pattern-matched list never needs.

1.5x vs 2x, for the vector case: below the golden ratio φ ≈ 1.618 the sum of previously freed buffers eventually exceeds the next request, so the allocator can reuse them — 1.5x does this, 2x never can (1+2+4 < 8, so it bumps forward forever). So 1.5x keeps peak memory and fragmentation lower (Folly, MSVC); 2x does fewer copies and is simpler (Rust Vec, libstdc++). For wok — the oracle tracks peak_bytes and there is no compacting GC to hide fragmentation — 1.5x is the better default if Array ever gains an amortized push-back.
The combination that actually fits wok: don't fuse them into one type. Put TRMC on the cons list (stack-safe, in-place producers) and a 1.5x push-back builder on Array (bulk, indexed), bridged by fromList/toArray. Each idea improves the type it belongs to. The unified do-everything sequence (RRB-tree) is a real option — defer it until profiling demands it.
