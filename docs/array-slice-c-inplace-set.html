Array Slice C — in-place set under rc == 1

Teach Array.set a fast path: when nobody else holds the array, poke the new value straight into the existing cell — zero allocation — instead of copying the whole thing. Same meaning, smarter memory. The FBIP rc == 1 gate, applied to a slot write.

Slice C reuses the rc == 1 gate from FBIP — not the drop_reuse/alloc_at token pairing. Arrays stay FBIP-excluded; this is a single, self-contained slot write.

1 · The idea in one line

set arr i v must return an array equal to arr but with slot i holding v. How it gets there is invisible to the program. Today it always builds a fresh copy. Slice C asks one question first — am I the only owner? — and if yes, mutates the one array it already has.

set arr i v
↓   is arr uniquely owned? (rc == 1)
YES → mutate in place0 array alloc · 0 array free
NO → copy-on-write+1 array alloc (today's behaviour)

3 · The fast path: in-place under rc == 1

If the refcount is 1, the prim owns the only reference. Nobody else can observe a change. So: drop the old element at slot i (cascade if it was a counted child), write v into that slot, leave the other n−1 slots exactly as they are. Same address, same refcount, no allocation, no spike.

4 · THE CRUX: one decision, two backends, bit-for-bit

wok keeps two runtimes in lockstep: a simple abstract model (the oracle’s source of truth) and the real C cell. A differential test runs every array program on both and demands identical memory stats. Because in-place and copy produce different stats, the rc == 1 answer must come out the same on both backends — or the oracle diverges.

abstract backend

refcount lives in the Cell; read it directly: cRc c. Non-destructive by nature.

C backend

refcount lives in the C cell. Today the only reader is wok_dec (which decrements). Add a peek: wok_rc(p).

→ same number, because both backends bump/drop the refcount at the same shared call sites ←

This isn’t a new leap of faith. FBIP already relies on the rc == 1 decision agreeing across backends at drop_reuse sites — and the oracle already proves it (a divergent decision would diverge the alloc count). Slice C reads the same lockstep quantity at a new site (set).

What makes it checkable, not just argued: the corpus must include a unique set (takes in-place) and a shared set (takes copy). Their alloc/free/peak_bytes differ, so any cross-backend disagreement on the gate fails the differential immediately.

6 · The contested design choices

axis 1 · the uniqueness probe

Non-destructive peek pick

Add wok_rc(p) (a WOK_PURE read of p->rc) + cRc on the abstract side. One read, no side effect, symmetric with the abstract backend.

axis 1 · alternative

Decrement-then-restore

Reuse wok_dec; re-wok_dup to undo. Writes the header twice, asymmetric with abstract. No upside.

axis 1 · rejected

Route through FBIP tokens no

That is the drop_reuse/alloc_at pairing the arc says not to build for arrays. Over-engineering for one slot write.

axis 2 · where the decision lives

One shared decision fn pick

arrayUnique :: Addr -> Store -> RC Bool hides the backend dispatch and returns one Bool. The “nodeCEligible discipline”: a single chokepoint, identical by construction.

axis 2 · alternative

Inline the rc read

A backend case inside arraySet. Works, but scatters the decision and is harder to unit-test in isolation.

axis 2 · impossible

Pure value predicate n/a

Uniqueness is heap state (the refcount), not a value property. Slice C reuses the discipline of nodeCEligible, not its purity.

axis 3 · what “in-place” means

One dispatching writer pick

C: literal wok_array_slot_set, same pointer. Abstract: replace the node at the same address, same rc/bytes, no recordAlloc/recordFree. Both ⇒ 0 alloc / 0 free.

7 · Why it’s sound

Sole owner ⇒ unobservable

rc == 1 means the prim’s owned reference is the only one. No other binding, structure slot, or continuation frame holds the array, so no one can see the mutation. The Perceus/FBIP argument, unchanged.

Bounds before mutation

i ≥ n ⇒ PrimError, array untouched — byte-identical to the copy path’s error. No partial write, no leak.

Old element + alias order

Read old slot → write v → drop old element (cascade if counted). Alias-robust even if v is the old element; v is moved in (no incref).

Oracle consequence to expect: unique-set programs already in the corpus will now report lower peak_bytes and 0 array alloc/free (no two-array overlap). The differential (backend-vs-backend) check self-adjusts — both take in-place. Any absolute/golden peak_bytes assertions must be updated to the new figures.
