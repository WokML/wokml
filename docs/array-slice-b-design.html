Array Slice B — a real C cell for Array a

What shipped: the wok array stopped being a Haskell-side simulation and became a genuine C allocator citizen — with byte-size-class placement and a bit-for-bit peak_bytes oracle. Plus where the array story goes next.

1 · The shift: interpreter-resident → real allocator layout

Before (Slice A), an Array a was an NArray [RCValue] living on the abstract IntMap heap — a model, not memory. Slice B gives the production (C) backend a real WokArray cell in the arena; the abstract NArray is kept only as the differential oracle’s reference to check the C cell against.

abstract backend (test oracle)

NArray [RCValue]

Stays on the IntMap heap. The simple, obviously-correct reference the C cell is proven equal to, program-by-program.

C backend (production)

WokArray cell

Real contiguous memory in the slab arena (or malloc for big ones). One allocation, one indirection, byte-accurate.

2 · The cell in memory

A 16-byte header (the WokObj prefix, with tag = WOK_ARRAY_TAG and the arity byte repurposed as elemkind) then a runtime len and the inline slots. Each slot is an 8-byte word: a flat scalar for Array U64, a pointer for boxed elements (this is exactly Koka’s vector).

3 · Where it lives: one byte-size class, shared with constructors

The arena’s free-lists are unified by total bytes: class = bytes/8 − 1. A constructor of arity a is class a; an array of length L is class L+1 — and they share the same free-list slot, so a freed array can be recycled as an equal-size constructor and vice versa.

4 · The invariant that proves it: peak_bytes

This slice promoted peak_bytes (the high-water of live heap bytes) from a C-only benchmark stat into a bit-for-bit differential-oracle invariant. The abstract heap now computes the bytes each node would occupy as a C cell (wouldBeCBytes: 8+8·arity for a constructor, 16+8·len for an array, 0 for anything that never becomes a C cell), and the oracle asserts it equals the C runtime’s own count on every test program.

5 · What this slice deliberately did NOT do

The brainstorm aimed at unboxed/flat arrays, but the codebase forced a sharper, smaller scope:

finding

Only U64 / U32 exist

No sub-word ints, no floats. So there are no element types denser than a word to pack.

finding

Scalars are already inline

A boxed Array U64 already stores the integers inline. So “flat” would be identical — no win today.

consequence

One polymorphic Array a

No Array→Vector rename, no new type, no allowlist. The flat-vs-boxed split dissolved.

Today set is copy-on-write (a whole new array). When the array is uniquely owned (rc==1), mutate the one slot in place — the FBIP gate applied to arrays.

slice D

Sub-word / float types + unboxed structs

This is when the deferred machinery earns its keep: add real U8/F64/… types, then pack them flat. Sub-word strides make peak_bytes rounding real; packed Vec4-style structs add the element layout descriptor + materialize-on-index.

later

Regions, String, ArrayOf n a

Effect-scoped arenas + LoCal serialization; String as flat bytes (not Array Char); and length-indexed ArrayOf n a — which the runtime len kept here already founds.

The throughline: Slice B is the real-memory foundation. Slice D is where the original “byte-size class + capacity rounding + packed structs” ideas finally pay off — once the language has the element types that make unboxing a genuine win.
