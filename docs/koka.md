# Koka Foundations: Row-Polymorphic Effects and Algebraic Handlers

A focused summary of Daan Leijen's three foundational papers for a designer of an ML-family language with HM core, record row polymorphism, monadic IO today, and algebraic effects planned for later.

**Papers:**
- Leijen, D. *Extensible records with scoped labels.* TFP 2005. <https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/scopedlabels.pdf>
- Leijen, D. *Koka: Programming with Row-polymorphic Effect Types.* MSFP 2014. <https://arxiv.org/pdf/1406.2061>
- Leijen, D. *Type Directed Compilation of Row-Typed Algebraic Effects.* POPL 2017. <https://www.microsoft.com/en-us/research/wp-content/uploads/2016/12/algeff.pdf>

## Paper 1 — Leijen 2005: Extensible Records with Scoped Labels (TFP)

This is the row theory that both Koka papers reuse verbatim for **effect** rows. Read this first; everything else builds on it.

### Row design: scoped/duplicate labels vs sets

Leijen takes a deliberately heretical position: **records and rows are allowed to contain duplicate labels, and duplicates are retained** (both in the value and the type).

> "A novel aspect of this work is that records can contain duplicate labels, effectively introducing a form of scoping over the labels."

The four mainstream alternatives are explicitly rejected:

1. **Lacks predicates (Gaster-Jones, TREX).** Extension is qualified: `{l = _|_} :: ∀rα. (r\l) ⇒ α → {r} → {l::α | r}`. Leijen calls this an "unnecessarily" restrictive choice: every use of a label leads to a lacks predicate, types balloon, and it forces qualified types into the host system.
2. **Presence/absence flags (Rémy).** Field types are `pre(τ)` or `abs`, polymorphic in a flag `ϕ`. Quote: "such type would not be obvious to the naïve user; especially since absent labels in the value can be present in the type."
3. **Subtyping (Cardelli-Mitchell).** Loses information about the other fields; needs an overriding operator on types.
4. **Wand's row variables with overwriting extension.** Provably incomplete (the canonical counterexample: `\r -> if True then {x=1 | r} else {x=2 | {}}` has two principal types `r = {x::Int}` or `r = {}`).

The scoped-label design dodges all of this by making extension **always** add a fresh layer (never overwrite) and treating duplicate labels as scopes.

### Row equality

Equality is defined as the smallest congruence over rows generated by these rules (Figure 1 of the paper):

```
(eq-head)   τ ≅ τ'    r ≅ s
            -----------------------------
            (|l :: τ | r|) ≅ (|l :: τ' | s|)

(eq-swap)   l ≠ l'
            -----------------------------
            (|l :: τ, l' :: τ' | r|) ≅ (|l' :: τ', l :: τ | r|)
```

The critical rule is `eq-swap`: **two adjacent fields commute if and only if their labels are different.** Distinct labels commute freely; equal labels do not. This is the entire technical novelty.

Corollary: `{x::Int, y::Int} ≅ {y::Int, x::Int}` but `{x::Int, x::Bool} ≢ {x::Bool, x::Int}`.

### Row extension when `l` is already in `r`

The answer is sharp: **extension is unconditional and never overwrites.** Both of these are well-typed and have the types shown:

```
{x = 2, x = True} :: {x :: Int, x :: Bool}
{x = True, x = 2} :: {x :: Bool, x :: Int}
```

Selection `r.l` and restriction `r - l` are defined to operate on the **first** matching label. To get at the shadowed value, you restrict and select again:

```haskell
{x = 2, x = True}.x          -- 2          (first x)
({x = 2, x = True} - x).x    -- True       (second x)
```

The motivating use case is local environment shadowing — `warning env f = f {color = red | env}` lets `f` recover the parent color by removing the first `color` field.

### No lacks/extension predicates needed

Crucial design payoff: because extension is total, the type signatures of the basic operations are exactly what a naive user expects, with **no qualified-type machinery**:

```
(.l)       :: ∀r α. {l :: α | r} → α
(- l)      :: ∀r α. {l :: α | r} → {r}
{l = _|_}  :: ∀r α. α → {r} → {l :: α | r}
```

> "The new notion of equality is the only addition needed to integrate our notion of records with a specific type system. Since no other concepts are introduced, the types of the primitive operations are basically what a naïve user would expect them to be."

### Unification (the algorithm a v2 implementation needs)

Three rewrite rules for matching a label `l` against a row `r` (Figure 3):

```
(row-head)   (|l :: τ | r|) ≃ (|l :: τ | r|) : []

(row-swap)   l ≠ l'    r ≃ (|l :: τ | r'|) : θ
             ----------------------------------------
             (|l' :: τ' | r|) ≃ (|l :: τ | l' :: τ' | r'|) : θ

(row-var)    fresh β, γ
             -------------------------------------------
             α ≃ (|l :: γ | β|) : [α ↦ (|l :: γ | β|)]
```

The full unification rule for two rows requires a **side condition** to prevent non-termination:

```
(uni-row)  s ≃ (|l :: τ' | s'|) : θ₁    tail(r) ∉ dom(θ₁)
           θ₁τ ∼ θ₁τ' : θ₂              θ₂(θ₁r) ∼ θ₂(θ₁s') : θ₃
           ----------------------------------------------------
           (|l :: τ | r|) ∼ s : θ₃ ∘ θ₂ ∘ θ₁
```

The side condition `tail(r) ∉ dom(θ₁)` is what makes the algorithm terminate on programs like `\r -> if True then {x=2|r} else {y=2|r}`. **TREX's unification fails to terminate on this case; Koka's does not.** This is a real bug-class you avoid by adopting scoped labels.

Unification is proved sound and complete (Theorems 1, 2). The proofs carry over directly to HM, qualified types, and MLF — that is, the row machinery is genuinely orthogonal.

### Implementation note for v2

For predicative type systems (i.e. HM), Leijen guarantees **constant-time field selection** via labeled vectors + constant folding (Section 8). When the row type is known statically the lookup becomes a compile-time constant; for open rows a worker/wrapper split floats the lookup outward. This matters because it kills the usual objection to extensible records ("slow selection").

## Paper 2 — Leijen 2014: Koka — Programming with Row-polymorphic Effect Types (MSFP)

This paper takes the 2005 row theory and **applies it to effects** instead of records. The key insight: an effect row is structurally identical to a record row, just with effect labels instead of field labels, and the type arguments are ignored when comparing labels.

### Effect rows on arrows: `a -> e b`

The function type constructor has kind `(*, e, *) -> *`:

```
(_ -> _ _) :: (*, e, *) -> *
```

So `τ₁ -> ε τ₂` says: take `τ₁`, possibly perform effect row `ε`, return `τ₂`. The middle argument is the row.

**Functions are uncurried by intent.** This is a deliberate departure from ML and Haskell:

> "As apparent from the type, functions need to be fully applied and are not curried. This is to make it immediately apparent where side effects can occur. For example, in ML, an expression like `f x y` can have side effects at different points depending on the arity of the function f. In our system this is immediately apparent, as one writes either `f(x, y)` or `(f(x))(y)`."

For an ML-family v2 that wants to keep currying, you can — but then `Int -> Int -> Int` has *two* effect rows and that's the price.

### What does `Int -> Int` mean?

Syntactic sugar: `τ₁ -> τ₂ = τ₁ -> ⟨⟩ τ₂` (the 2014 paper writes this explicitly in Figure 1). So a bare arrow is **closed total**. But:

- For **let-bound** values, Koka **opens** function types at instantiation. A let-bound `id : ∀α. α → α` becomes `∀αµ. α → µ α` at each use site. (Section 3.2.)
- For **lambda parameters**, the type stays as written — no opening. (Otherwise principal types would be lost.)

This is the crucial trick that makes "is `Int -> Int` total or polymorphic?" not a meaningful question for users. **The displayed type is closed and total; the operationally-used type is open.** Internally everything is row-polymorphic.

> "The solution we adopted in Koka is to actually close all the types of let-bound variables according the above rule, and at instantiation of such let-bound variable, we open the type again, introducing a fresh µ for any function type with a closed effect."

This pattern is mandatory for the system to feel ML-like rather than Haskell-with-extra-noise.

### Effect stratification

Predefined aliases (Section 2.2):

```
alias total = ⟨⟩
alias pure  = ⟨exn, div⟩
alias st<h> = ⟨alloc<h>, read<h>, write<h>⟩
alias io    = ⟨st<ioheap>, pure, ndet⟩
```

Basic effect constants: `total, exn, div, ndet, alloc<h>, read<h>, write<h>, io`.

Note these are **not** a subtyping lattice — they're just aliases for closed effect rows. `pure` is exactly `⟨exn, div⟩` and corresponds to "Haskell purity". `io` is the kitchen sink that includes everything.

Sample primitive types:

```
random : ()                  → ndet double
print  : string              → io ()
error  : ∀α. string          → exn α
(:=)   : ∀α. (ref<h,α>, α)   → write<h> ()
```

### Effect equality (row equivalence)

Identical to the 2005 record rule, with one subtlety:

```
(EQ-HEAD)   ε₁ ≡ ε₂
            ----------------------
            ⟨l | ε₁⟩ ≡ ⟨l | ε₂⟩

(EQ-SWAP)   l₁ ≢ l₂
            ---------------------------------
            ⟨l₁ | ⟨l₂ | ε⟩⟩ ≡ ⟨l₂ | ⟨l₁ | ε⟩⟩

(UNEQ-LAB)  c ≠ c'
            ----------------------------
            c⟨τ₁..τₙ⟩ ≢ c'⟨τ'₁..τ'ₙ⟩
```

The subtle part: **label comparison ignores type arguments**, so swapping is purely on the constant. The one exception is `st<h>`: `st<h₁> ≢ st<h₂>` when `h₁ ≠ h₂` (so distinct heap variables count as distinct labels and may commute).

### Duplicate effect labels: not a bug, a feature

`⟨exn, exn⟩ ≢ ⟨exn⟩`. The paper defends this strongly. Two payoffs:

1. **Principal unification without extra constraints.** Without duplicates, `⟨exn | µ⟩ ∼ ⟨exn⟩` has two solutions (`µ = ⟨⟩` or `µ = ⟨exn⟩`); with duplicates allowed there is only one (`µ = ⟨⟩`). This is the Wand incompleteness problem solved structurally.

2. **Clean types for elimination forms.** `catch` discards exactly one exn layer:

   ```
   catch : ∀αµ. (() → ⟨exn | µ⟩ α, exception → µ α) → µ α
   ```

   If the handler can itself throw, `µ` unifies with `⟨exn | µ'⟩` giving the action effect `⟨exn | exn | µ'⟩` — and that's the right answer. The presence-flag alternative requires a polymorphic flag `ϕ` on `exn` and gives a much uglier type.

3. **Injection.** `inject : ∀µα. (() → ⟨exn|µ⟩ α) → (() → ⟨exn|exn|µ⟩ α)` lets you hide an inner exception under an outer handler — a real operation, not just a typing artifact.

### Effect generalization and the value restriction

This is where Koka does something unusual and very relevant for the migration question.

The declarative `GEN` rule (Figure 3):

```
(GEN)   Γ ⊢ e : τ | ⟨⟩    α ∉ ftv(Γ)
        ----------------------------------
        Γ ⊢ e : ∀α. τ | ε
```

**Generalization is only allowed when the effect is total `⟨⟩`.** Similarly for `LET`:

```
(LET)   Γ ⊢ e₁ : σ | ⟨⟩    Γ, x : σ ⊢ e₂ : τ | ε
        -----------------------------------------
        Γ ⊢ let x = e₁ in e₂ : τ | ε
```

This is the **semantic value restriction**. Note what is *not* required: there is no syntactic check that `e₁` is a value. The classical ML unsoundness

```
let r = ref [] in (r := [true], !r + 1)
```

is rejected here because `ref []` has effect `alloc<h>` (not `⟨⟩`), so generalization is forbidden. Critically:

> "In contrast to the value restriction, we can still generalize over any expression that is not stateful regardless of its syntactic form."

Practically: pure computation like `let x = compose f g in ...` generalizes even though `compose f g` is not syntactically a value. ML's value restriction would refuse; Koka's effect-restriction accepts. This is a clean win.

(The paper also mentions extending to allow `exn, div` at generalization is sound, but it's left for the practical implementation, not the formal one.)

### `runST` as a row operation

```
run : ∀µα. (∀h. () → ⟨st<h> | µ⟩ α) → µ α
```

The `RUN` rule:

```
(RUN)   Γ ⊢ e : τ | ⟨st<ξ> | ε⟩    ξ ∉ ftv(Γ, τ, ε)
        --------------------------------------------
        Γ ⊢ run e : τ | ε
```

If the heap variable doesn't appear in the environment, return type, or remaining effect, you can strip `st<h>` from the row. Koka **automatically inserts `run` at generalization points** when applicable, so internal mutability disappears from the inferred type. This is how `formatInline` in the Markdown example gets inferred as `total` despite using a mutable string builder.

The paper proves heap safety formally (Section 5.2 — first such proof for a strict language with exceptions and divergence) and proves the deep semantic theorems:

- **Theorem 2 (Exceptions):** If `exn ∉ ε` then `e` never reduces to `throw c`.
- **Theorem 3 (State):** If `st<h> ∉ ε` then `e` never reduces to a heap-bound answer.
- **Theorem 4 (Divergence):** If `div ∉ ε` then `e` terminates.

> "Contrast the results of this section to many other effect systems that just use effect types as syntactic 'labels'. In our case the theorems of this section are truly significant as they show there is a deep correspondence between the effect types and the dynamic semantics."

These theorems are what justify the whole exercise. Without them, effect rows are decorative.

### Subtyping vs unification — Koka chose unification, deliberately

There is no effect subtyping in Koka. This is stated explicitly:

> "This is the choice made in an earlier version of Koka described as a technical report [Tate-Leijen 2010]. However, in our experience with that system in practice we felt the constraints often became quite complex and the combination of polymorphism with subtyping can make type inference undecidable."

The replacement for subtyping is **row-polymorphic openness**: every let-bound function type, on instantiation, gets a fresh `µ` tail, so a call site `foo(f, g)` automatically unifies whatever effects `f` and `g` have into a common row.

That is: **a "pure" function is not a subtype of an "effectful" one. Instead, the pure function's type, at every use site, gets opened to be polymorphic in its effect tail, so unification finds the right row.**

For the inferred type of `foo(f, g) = f(); g(); error("hi")`:

```
foo : ∀µ. (() → ⟨exn | µ⟩ (), () → ⟨exn | µ⟩ ()) → ⟨exn | µ⟩ ()
```

Both `f` and `g` are forced to the same `µ`. Looks restrictive but isn't: at call sites, each argument has its own fresh open row, and unification combines them.

### Inference algorithm

Algorithm W with effect-row unification (Figures 8 and 9). The unification rules are literally the 2005 rules with `ε ≃ l | ε' : θ` doing the row rewrite. The `LET` rule applies `gen` only after checking `ε₁ ∼ ⟨⟩`.

## Paper 3 — Leijen 2017: Type Directed Compilation of Row-Typed Algebraic Effects (POPL)

This paper takes the 2014 type system and adds **algebraic effect handlers** as the user-definable effects, while keeping the same row theory.

### The headline: the type system barely changes

> "The calculus and its type system has been in use for many years now and has been developed from the start using effect types based on rows with scoped labels. Originally, user-defined effects were described using a monadic approach but it turns out that algebraic effects fit the original type system well with almost no changes."

This is the migration answer in one sentence. The 2014 effect rows are exactly what you need to host handlers later. You do not redesign the type system; you add a `handle` construct and an effect-declaration syntax.

### Surface syntax

Effect declaration:

```koka
effect exc {
  raise( s : string ) : a
}
```

This populates `Γ₀` with `raise : string → exc a` and adds `exc` to a signature env `Σ(exc) = {raise}`.

Handler:

```koka
fun catch(action, h) {
  handle(action) {
    raise(s) → h(s)
  }
}
```

`handle{h}(e)` desugars from `handler{h}` which is `λf. handle{h}(f())`. Each operation clause binds a `resume` continuation; the `return x → e` clause transforms the final value.

Parameterized handlers (for state):

```koka
val state = handler(s) {
  return x → (x, s)
  get()    → resume(s, s)
  put(s')  → resume(s', ())
}
```

### Handler typing rule

```
Γ ⊢ e : τ | ⟨l | ε⟩    Σ(l) = {op₁..opₙ}
Γ, x : τ ⊢ er : τr | ε
Γ ⊢ opᵢ : τᵢ → ⟨l⟩ τᵢ' | ⟨⟩
Γ, resume : τᵢ' → ε τr, xᵢ : τᵢ ⊢ eᵢ : τr | ε
------------------------------------------------------------------------
Γ ⊢ handle{ op₁(x₁)→e₁; ...; opₙ(xₙ)→eₙ; return x→er }(e) : τr | ε
```

Two things to note:
1. The handled computation has effect `⟨l | ε⟩`; the result has effect `ε`. The handler **discharges exactly one layer of `l`** from the row. Scoped labels make this clean: if the body itself uses `l` internally under another handler, only the outermost is stripped.
2. `resume : τᵢ' → ε τr` — resume is typed with the **outer** result effect, because resuming continues evaluation under the same handler.

### Deep vs shallow

Koka uses **deep handlers** — the captured continuation is re-wrapped in the same handler:

> "Resuming under the same handler is important as it ensures that our semantics correspond to the original categorical interpretation of algebraic effect handlers as a fold over the effect algebra. If the continuation is not resumed under the same handler, it behaves more like a case statement doing only one level of the fold. Such handlers are sometimes called shallow handlers."

The reduction rule (Figure 4) shows this directly:

```
handle{h}(Xop[op(v)]) → e[x ↦ v, resume ↦ λy. handle{h}(Xop[y])]
                                         ^^^^^^^^^^^^^^^^^^^^^^^
                                         re-wrapped in same handler
```

Deep handlers are the default well-behaved choice and what the type rule above assumes. Shallow is a power-user variant; don't worry about it for v1 of the swap.

### Nested handlers of the same effect — this is where scoped rows pay off

The `Xop` evaluation context skips through handlers that don't handle the operation:

```
Xop ::= [] | Xop(e) | v(Xop) | val x = Xop; e
      | handle{h}(Xop)                            if op ∉ h
```

So `handle{h}(...)` "captures down to the nearest enclosing handler containing a clause for `op`". With scoped labels, the row `⟨exc | ⟨exc | ε⟩⟩` is **a legal, distinct type** representing two nested exception handlers. The outer one handles only what escapes the inner. The `inject` operation from 2014 is the surface-level way to introduce this.

> "The system also allows duplicate labels, where an effect ⟨exc, exc⟩ is legal and different from ⟨exc⟩. There are some use-cases for this but in practice we have not found many uses for duplicate effects (nor any drawbacks)."

You couldn't do this with set-based rows or with absence-flag rows — duplicates would collapse to a single label and the type system couldn't distinguish "inner exn" from "outer exn".

### Effect generalization: unchanged from 2014

The same `⟨⟩`-only generalization rule applies. No new value-restriction issues are introduced by handlers.

The 2017 paper also formalizes the **simplification rules** that 2014 only sketched: `OPEN` and `CLOSE` rules let inference simplify let-bound types to their closed form for display, while opening them at each use site. The key claim:

> "Due to OPEN this is not the case: at every occurrence of such let-bound variable the rule OPEN can always be applied (possibly surrounded by INST/GEN) to lead to the original most general type – i.e. even though the types are simplified, the set of typeable programs is unchanged."

These rules also have a performance role in the CPS translation (more handled effects = fewer functions that need CPS).

### Subtyping: still none

The same approach — no subtyping, just open/close. The paper goes further on the design dimension:

> "Many other type systems use structural types for the effects where each effect operation (and its type) occurs in the inferred types. In this paper we use a nominal system where a single effect type implies the available operations. We believe this is better in practice to keep inferred types small and understandable."

Compare a state-handler type:

```
Koka:  state : (s, () → ⟨state<s> | e⟩ a) → e (a, s)
Links: state : (s) -> (Comp({Get:s, Put:(s){}->()|e}, a))
                          -> Comp({Get{_}, Put{_}|e}, a)
```

Nominal effect labels (= what Koka does) keep types compact. Structural effect rows (= Links, Frank, Eff) expose every operation but make types unwieldy.

### Handler compilation: type-directed selective CPS

This is the part you probably don't have to think about today, but it constrains a future decision:

> "We use a type directed selective CPS translation. We built on the translation by Nielsen who introduces a sound selective CPS translation for the simply typed lambda calculus extended with callcc and throw. However, the translation by Nielsen applies to monomorphic effects only and we will see that in the presence of polymorphic effect variables the translation becomes more complex."

Only functions whose effect row contains a *user-defined* (handled) effect get CPS-transformed. Built-in effects (`exn, div, ndet, st, io`) compile directly. Functions polymorphic in their effect variable get **two compiled versions** (CPS and direct), and the wrapper picks at runtime based on whether a continuation argument was passed:

```
val map = λ(xs, f, k). if k? then map_cps(xs, f, k) else map_plain(xs, f)
```

This polymorphic duplication is a real engineering cost; for the Koka core library it added ~20% to code size. The `OPEN`/`CLOSE` simplification reduced the set of CPS-translated functions by **>80%** in their core library.

For an OCaml-style native runtime you could capture the stack directly (one-shot continuations as in multicore OCaml) instead of CPS — but that's a runtime choice, not a type-system choice.

## Cross-cutting answers to the design questions

### Row design summary

| Choice | Cost | Payoff |
|---|---|---|
| Scoped labels (duplicate-allowed) | Slightly counterintuitive at first | Principal unification with no qualified types, no presence flags, no lacks predicates; nested handlers of same effect just work |
| Sets / lacks predicates | Heavy qualified-type machinery in the elaborator; large inferred types | "Cleaner" types when no duplicates needed |
| Presence/absence flags | Extra kind machinery; flag-polymorphic types | Can express absence positively |

**Recommendation:** scoped labels for both records and effects. Same row machinery, one implementation. This is also what Frank converged on, and what Koka has shipped for over a decade.

### Arrow type recommendation

- Make `a -> b` mean `a -> ⟨⟩ b` syntactically (closed total).
- Internally, **open** every let-bound function type at each instantiation site (introduce a fresh `µ` tail for every closed effect row in the function's type).
- Don't open lambda-bound parameter types — that breaks principality.
- Display closed types to users; carry open types in the elaborator.

This is the only way to get a system that "looks like ML" on the surface while threading effects correctly.

### Effect generalization rule

Use the semantic value restriction:

```
generalize when the inferred effect of the rhs is ⟨⟩ (or, optionally, ⊆ ⟨exn, div⟩)
```

This dominates ML's syntactic value restriction. It admits more programs (any pure computation, regardless of syntactic form), and it's the only restriction needed to keep mutable references sound under let-polymorphism.

### Handler semantics for the future swap

When you swap monadic IO for algebraic handlers:

- **Deep handlers** by default (resume re-wraps in the same handler — required for the categorical fold semantics).
- The handler typing rule **discharges exactly one effect label from the row** of the action, leaving everything else.
- `resume`'s codomain effect is the **outer** effect (not the action's effect) — this is what makes resumption "continue under the same handler" type-check.
- Use **nominal** effect declarations (`effect exc { raise : string → a }`), not structural rows of operations. Nominal stays compact at scale; structural reads better in toy examples but kills you in practice.
- Allow `handle` to discharge the outermost matching label only; nested same-effect handlers compose because the row `⟨l | ⟨l | ε⟩⟩` is a legitimate type and the evaluation context for operations naturally skips inert frames.

### Subtyping vs unification

No subtyping. Use HM unification + automatic opening of let-bound function types. Koka tried subtyping in 2010, gave up by 2014, and never looked back.

If users want to pass a pure function where an effectful one is expected, that "just works" because the pure function's let-bound type opens to `∀µ. a → µ b` at each use site, and unification picks the required effect.

### Migration path — what to lock in NOW

**Do these now and the swap is mechanical:**

1. **Effect rows on the arrow constructor with kind `(*, e, *) → *`.** Even if today you only ever produce `⟨⟩` or `⟨io⟩`, the row slot must be in the AST and the unifier. Adding it later means rewriting every function type.

2. **Scoped-label row equality and unification** (with the `tail(r) ∉ dom(θ)` termination side condition — do NOT skip this, TREX-style implementations fail on innocuous-looking programs). Use it for both records and effects so you have one implementation.

3. **Open/close transformation at let-binding boundaries.** Store closed types in let-binding schemes; open them on instantiation (replace each closed effect `⟨l₁..lₙ⟩` on a function arrow with `⟨l₁..lₙ | freshµ⟩`). Display closed forms to users.

4. **Semantic value restriction:** generalize iff `ε = ⟨⟩`. Not the syntactic ML restriction. Don't bake `is_syntactic_value(e)` into the generalization check.

5. **Treat `io` as a single nominal effect label today.** When you swap to algebraic handlers, `exn`, `state<h>`, `console`, `async`, etc. become individual effect labels that you split off from `io`. If `io` is one opaque label, the type-system change is invisible to existing user code (it still type-checks as having effect `⟨io⟩`), and you opt-in to finer effects per module.

6. **No effect subtyping.** Resist the temptation. It's the trap Koka explicitly fell into and climbed back out of.

7. **Nominal effect declarations** (not structural). An effect is a named label backed by a signature `Σ(l) = {op₁..opₙ}`. The label appears in types; the operations do not.

8. **Per-effect kind discipline.** Effect labels have kind `k`; rows have kind `e`. Distinguish them in the kind system from the start so users can't write `⟨Int⟩` or similar nonsense.

**Things that would force a rewrite if you got them wrong:**

- Picking lacks predicates / Gaster-Jones rows — you'd need to remove the entire qualified-types machinery before you could add scoped handler-nesting.
- Picking Rémy presence flags — you'd need to redesign the kind system.
- Adding effect subtyping — the resulting constraint solver would not have a clean migration to row unification.
- Using ML's syntactic value restriction — once user code relies on its quirks (`let x = (compose f g) in ...` works only if eta-expanded), you can't safely move to semantic value restriction.
- Currying function types **without** putting effect rows on every arrow — a Haskell-style `a -> b -> c` with effects only on the outermost arrow gives wrong semantics for partial application; either go uncurried like Koka or put a row on every arrow.

**Things that are safe to defer:**

- The actual `handle`/`effect` surface syntax — purely additive.
- The handler compilation strategy (CPS vs direct stack capture) — runtime choice, type system is unaffected.
- The decision between deep and shallow handlers — type rule for deep handlers is the principled default; shallow is a later extension.
- `run`-style heap encapsulation — additive once you have effect rows and the `⟨⟩`-only generalization rule.
- The OPEN/CLOSE display simplification — purely a UX tweak on inferred types.

### One concrete sketch of the v1 → v2 transition

**v1 (today):**

```
-- single io effect label
print : string -> ⟨io⟩ ()
read_file : string -> ⟨io⟩ string
sqr : int -> int            -- closed total, opens to ∀µ. int → µ int at use sites
```

**v2 (after swap), no change to user types initially:**

```
-- io is now an alias
alias io = ⟨exn, async, fs, console, st<ioheap>, ndet⟩

-- existing code still type-checks; ⟨io⟩ expands to the row above
-- new code can be finer-grained:
parse_int : string -> ⟨exn⟩ int
```

The instant `io` is an alias for a row of finer labels, users opt into precision per function. No syntactic migration of existing call sites. This is exactly the path Koka took from 2014 to 2017.
