# Wok v1 BNFC Grammar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers-extended-cc:subagent-driven-development (recommended) or superpowers-extended-cc:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a BNFC grammar for the `wok` language that lex+parse+pretty-print round-trips, with zero parser conflicts.

**Architecture:** Single `grammar/Wok.cf` file drives BNFC's Haskell backend, generating `Wok.{Abs,Lex,Par,Print,Layout,ErrM}` into `src/Wok/`. Grown incrementally — each task adds a slice of the language and is independently testable. The CLI executable parses a `.wok` file and prints the AST via the generated `Print.hs`; golden tests pin down the AST shape for a sample corpus.

**Tech Stack:** Haskell (GHC 9.10), Cabal 3.14, BNFC (parser-generator), Alex (lex), Happy (parse), Tasty + Tasty-Golden (tests).

**Reference spec:** `docs/superpowers/specs/2026-05-20-bnfc-wok-grammar-design.md`

**Why files are organized this way:**

- One example file per feature so test failures localize to a specific grammar addition.

- [ ] **Step 1: Add token definitions to `Wok.cf`**

Replace the body of `grammar/Wok.cf` with:
```bnfc
-- wok grammar v1 (Task 2: + idents + string/char)

entrypoints Module ;

Module.   Module ::= [Decl] ;
DExp.     Decl ::= Exp ;

separator Decl ";" ;

-- Expression forms (just enough to test lexer)
EVar.     Exp ::= VarId ;
EOp.      Exp ::= VarSym ;
EWild.    Exp ::= "_" ;
ELitI.    Exp ::= Integer ;
ELitS.    Exp ::= String ;
ELitC.    Exp ::= Char ;

-- Identifier token classes (spec section: Lexical layer)
-- VarId: starts with letter or `_`; mid/end allows letters, digits, `_`, `'`, `-`
position token VarId
  (letter | '_') (letter | digit | '_' | '\'' | '-')*
  ;

-- VarSym: pure symbol run
position token VarSym
  ('!' | '#' | '$' | '%' | '&' | '*' | '+' | '.' | '/' |
   '<' | '=' | '>' | '?' | '@' | '\\' | '^' | '|' | '-' | '~')+
  ;

comment "--" ;
comment "{-" "-}" ;
```

NOTE on `_`: BNFC will lex `_` as a literal because we use `"_"` in the `EWild` rule. Literals win on ties against tokens by BNFC's longest-match-then-keyword rule. Longer underscore-containing idents (`_x`, `_unused`) will match VarId.

NOTE on reserved-tokens: `->`, `=`, `\`, `|`, `:`, `::` will become reserved when introduced in later tasks. For now they would lex as VarSym, which is OK — we're not yet parsing constructs that use them.

```bnfc
-- wok grammar v1 (Task 3: top-level decls)

entrypoints Module ;

Module.   Module ::= [Decl] ;

DEqn.     Decl ::= FunLHS "=" Exp ;
DSig.     Decl ::= VarId [VarIdComma] ":" Type ;       -- multi-name sig
DData.    Decl ::= "data" VarId [VarId] "=" [ConDef] ;
DFixity.  Decl ::= "fixity" FixName FixAssoc [FixRel] ;

separator Decl ";" ;

-- Helper: comma-separated additional VarIds for multi-name sigs (`f, g, h : T`)
-- BNFC lists handle "0 or more"; "1 or more" needs a separate non-empty rule.
VICons.   VarIdComma ::= "," VarId ;
separator VarIdComma "" ;

-- For `data T a b c = ...`, type params are bare VarIds
separator VarId "" ;

-- Function LHS (prefix only for Task 3)
LHSPre.   FunLHS ::= FunName [AtomPat] ;
FNBare.   FunName ::= VarId ;
FNBareSym. FunName ::= VarSym ;

-- Patterns (atom level only for Task 3)
APVar.    AtomPat ::= VarId ;
APWild.   AtomPat ::= "_" ;
APLitI.   AtomPat ::= Integer ;
APParen.  AtomPat ::= "(" AtomPat ")" ;

separator AtomPat "" ;

-- Constructor definition body for `data`
ConDef.   ConDef ::= VarId ;                            -- 0-arg only for Task 3; widen in Task 8
separator ConDef "|" ;

-- Types (atom level only for Task 3)
TVar.     Type ::= VarId ;

-- Fixity decls
FNFSym.   FixName ::= VarSym ;
FNFAlpha. FixName ::= VarId ;

FALeft.   FixAssoc ::= "left" ;
FARight.  FixAssoc ::= "right" ;

FRTight.  FixRel ::= "tighter" "than" FixName ;
FRLoose.  FixRel ::= "looser" "than" FixName ;

separator FixRel "" ;

-- Expressions (atom level only for Task 3)
EVar.     Exp ::= VarId ;
ELitI.    Exp ::= Integer ;
ELitS.    Exp ::= String ;
ELitC.    Exp ::= Char ;

-- Token definitions (carried forward from Task 2)
position token VarId
  (letter | '_') (letter | digit | '_' | '\'' | '-')*
  ;

position token VarSym
  ('!' | '#' | '$' | '%' | '&' | '*' | '+' | '.' | '/' |
   '<' | '=' | '>' | '?' | '@' | '\\' | '^' | '|' | '-' | '~')+
  ;

comment "--" ;
comment "{-" "-}" ;
```

NOTE: We introduce reserved tokens `=`, `:`, `data`, `fixity`, `left`, `right`, `tighter`, `looser`, `than`, `|`. These will be recognized by BNFC's keyword-table mechanism automatically because they appear as literals in rules.

KNOWN ISSUE TO WATCH: BNFC may emit a shift/reduce warning at the `Decl ::= ...` level because four alternatives share the same prefix-token possibility (`VarId` could start either `DEqn` or `DSig`). The grammar should be LALR(1) — disambiguation is by lookahead on `=` vs `:`. Verify in Step 2 below.

## Task 5: Infix expressions (operator chain with deferred precedence)

**Goal:** Add the `[InfixTail]` extension to `Exp` so operator chains parse as `head + [(op, operand), ...]`. Precedence/associativity is deferred to the resolver pass; the grammar just collects the flat chain.

**Files:**
- Modify: `/Users/zy/wokml/grammar/Wok.cf`
- Regenerate: `src/Wok/*`

**Acceptance Criteria:**
- [ ] `1 + 2` parses as `EExpr (AppExp [1]) [ITail (IOSym +) (AppExp [2])]`
- [ ] `1 + 2 * 3` parses as `EExpr 1 [(+,2), (*,3)]` (flat tail of two)

NOTE: BNFC accepts `position token Integer ...` to override the built-in `Integer` token class.

**Wart confirmation:** with this rule, `1-2` lexes as `Integer 1` + `Integer -2` because the second token starts at `-` and greedily eats the digit. This matches the spec's documented wart.

**Subtle issue:** the previous `VarSym` token already matched `-` (via `'-'` in its char set). The longest-match rule means a `-` followed by a digit will prefer `Integer` (which is 2+ chars long, vs `VarSym -` which is only 1). When `-` is followed by a non-digit, `VarSym` matches.

There may be ambiguity with `--` (line comment) — but BNFC's `comment "--"` is processed *before* the lex rules. So `--foo` is still a comment, not `Integer -` + `-foo`.

parseToBS :: FilePath -> IO BL.ByteString
parseToBS path = do
  src <- readFile path
  let toks = Lay.resolveLayout True (L.tokens src)
  case P.pModule toks of
    E.Bad msg -> pure $ BL.pack ("PARSE ERROR: " ++ msg ++ "\n")
