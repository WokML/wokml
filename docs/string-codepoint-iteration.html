How wok loops over a string's characters

Codepoint iteration without touching the machine core — and why an ordinary wok loop survives effects when a hidden Haskell loop doesn't.

1 · The machine carries a to-do list

wok runs your program on a small machine that holds an explicit to-do list (its "continuation"). When code performs an effect — a handler pausing, a generator yielding — the machine grabs everything still on the list and saves it, so it can resume later. The iron rule: it can only capture work that is actually on the list.

2 · Two ways to build foldChars

We want foldChars f acc s: walk the string left to right, calling your function f on each character to build up an accumulator. There are two ways to write it.

the heavy way

One big primitive

A single built-in that runs its own loop in Haskell, calling f once per character. To make effects work, it needs a brand-new part bolted into the machine's continuation code.

the simple way

Decompose

A tiny built-in that decodes one character at a byte offset. The loop is then ordinary recursive wok code on top. No machine-core change — it's exactly how Array.map already works.

4 · How the simple loop actually runs

The built-in never loops — it only decodes a single character. wok does the walking, threading a byte offset that jumps by each character's width (UTF-8 characters are 1–4 bytes).

-- two tiny first-order primitives (no closures, no looping)
extern decodeCharAt : String -> U64 -> Char   -- byte offset in, character out
extern charWidthAt  : String -> U64 -> U64    -- that character's byte width (1..4)

-- foldChars is now ordinary wok library code
foldChars f acc str = foldGo f acc str 0 (byteLength str)

foldGo f acc str off end =
  case off >= end of
    True  -> acc
    False -> foldGo f (f acc (decodeCharAt str off))
                   str (off + charWidthAt str off) end

Walking "café" with a fold that counts characters (the é takes 2 bytes, so the offset jumps 3 → 5):

read 'c'
0count 1
read 'a'
1count 2
read 'f'

read 'é' (2 bytes)

5 ≥ 5: stop
5return 4

fig 4 — the badge is the byte offset. One pass, no heap allocation in the loop; the offset advances by codepoint width.

The point: the simple version touches none of the machine's continuation code — the very place past slices hid use-after-frees. It gives up the "reusable closure-driving frame," but nothing actually needs that frame: arrays, bytes, and codepoints all have indexed access, so each one decomposes into a one-step primitive plus a plain wok loop. The frame would only ever be forced by a source with no indexed access — and a string isn't that.
