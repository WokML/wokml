1 · The waste FBIP removes

Run map f [1,2,3] today. The three old Cons cells die on the way down the list; three brand-new Cons cells are born on the way back up. Same shape in, same shape out — but the allocator did three frees and three allocations for a list that never changed length.

2 · Terms, defined once

Everything below is built from these. Skim them now; the diagrams reuse them verbatim.

cellOne heap-allocated value: a small header (rc, tag, arity) followed by its fields. A list node Cons x rest is a 2-field cell.
refcount (rc)How many live references point at a cell. The runtime keeps this number. wok has no garbage collector — a cell is freed the instant its rc hits 0.
uniquerc == 1: you hold the only reference. Nobody else can observe the cell, so it is safe to recycle it in place. This is the whole license for FBIP.
PerceusThe compile-time pass (Reinking et al., 2021) that inserts the dup/drop calls so refcounts stay correct. wok already runs it; FBIP extends it.
dup / drop__rc_dup x increments x's rc (take a co-owner). __rc_drop x decrements it (release; free at 0). The cell's last drop is where reuse can happen.
cascadeWhen a cell is freed, the refs it held to its children are dropped in turn — which may free them, recursively. FBIP keeps this; it only changes what happens to the parent shell.
drop_reuseA last-drop that, when the cell is unique, releases the children (the cascade) but returns the empty shell instead of handing it to the free list.
alloc_atAn allocation that accepts a reuse token: if the shell fits, re-stamp its header and overwrite its slots; otherwise allocate fresh.
reuse tokenA one-use ticket passed from drop_reuse to alloc_at — either a real freed shell, or NULL (cell was shared, nothing to reuse).
arityThe number of fields in a cell. In wok a cell is 8 + 8×arity bytes, so arity fixes the byte size — "same size" and "same arity" are one question.
descriptorA per-constructor table (keyed by tag) recording each slot's kind — wok's "info table". It tells alloc_at the shell's size statically.
immediateA nullary constructor (Nil, None, True) stored inline with no cell at all. It has no shell, so it is never a reuse donor.
abstract heapThe reference backend: cells live as entries in an IntMap. Easy to inspect; used as the oracle's source of truth.
C arenaThe real backend: a slab allocator with a freelist[arity] per size class. The production memory path.
differential oracleThe test harness that runs both backends on every program and asserts the output is bit-for-bit identical and the alloc/free/peak counts match.

4 · Two operations and a one-use ticket

FBIP splits the work into a matched pair, exactly as Koka does. A drop that would have freed a unique cell instead hands back the empty shell as a reuse token; a later allocation of the same size accepts that token and re-stamps the shell in place.

fig 4 — drop_reuse → token → alloc_at. Either box can bail to the safe slow path (dotted).

5 · What reuse does to one cell

The shell keeps its address. Its children are released (their refcounts drop, cascading if they hit zero), the header is re-stamped (fresh count, possibly a new constructor tag), and the slots are overwritten with the new fields. Nothing about the cell's identity is observable to the program — this is the data-rewrite that makes pure code fast.

Cons @0x40rc 1
slot 0x
slot 1→ rest
→
Cons @0x40rc 1
slot 0f x
slot 1→ map f rest

fig 5 — same block at 0x40, same arity, new contents. The old x / rest refs were released first.

Size must match exactly. A wok cell is 8 + 8×arity bytes — size is a pure function of arity, so "same byte size" and "same arity" are the same question. Reuse only fires arity-for-arity. The tag may change (a 2-field Cons shell could become any other 2-field constructor); the count of slots may not.

6 · The gate: reuse is earned at runtime

The compiler pairs a drop with an allocation statically, but whether the cell is actually recycled is decided at runtime by its reference count. This is what makes FBIP safe without a clever uniqueness proof: if the cell is shared, you simply allocate fresh.

drop_reuse: decrement the count
↓
count hit 0 (unique)release children, return the shell as the token — 0 frees, 0 allocs across the pair
count still > 0 (shared)token is NULL; alloc_at allocates a fresh cell — identical to today

fig 6 — the MVP gate. Static "this is provably unique, skip the check" is a later specialization.

7 · One map step, refcount by refcount

Here is a single iteration of map f (Cons x rest) when the Cons cell is unique. Follow the cell's rc and the two children. The key move is steps 2–3: the alt dups the children it keeps, then drop_reuse releases the cell's own refs to them — ownership of x and rest transfers from the dying cell to the new bindings, perfectly balanced, while the shell falls out as a token.

#what runsConsxrest
1match Cons x rest — read the two slots (no counts change yet)1km
2dup x; dup rest — the alt keeps both (for f x and the recursion)1k+1m+1
3drop_reuse(Cons) — 1→0, unique; release the cell's child refs; keep the shell as tokentokenkm
4rest' = map f rest — recurse; the token rides in the pending continuationheldkm−1
5y = f x — consumes the kept x unitheldk−1·
6alloc_at(token, Cons, y, rest') — reuse the shell; write the new slots1··
7return the cell — same block, new contents1··

fig 7 — k, m are whatever the children's counts were on entry; they end exactly one lower (the cell's old ref to each is gone). The cell itself: in at rc 1, out at rc 1, never freed, never allocated.

Reading the dance: dup (+1) then drop_reuse's child-release (−1) cancel for x and rest — net zero, the references just moved from the cell's slots into y = f x and the recursive call. If the cell had not been unique at step 3, drop_reuse would have only decremented it (still alive for the other owner) and returned NULL, and step 6 would allocate fresh — same answer, one real alloc.

8 · A map, allocation by allocation

Now zoom out to the whole list. The token from each step is held across the recursive call (it rides in the pending continuation, as in step 4 above). On the way back up, each held shell is the cell the new Cons is built into. Watch the running allocation count.

fig 8 — three shells held at the bottom become the three new shells on the way up. 0 allocs, 0 frees vs. today's 3 + 3.

The deliverable is the count, not the clock. The interpreter makes no wall-clock claim. The win is the deterministic, oracle-visible collapse in allocation count: map over N elements goes from 2N allocator events to ~0. (For a tail-recursive accumulator like reverse, the token is consumed immediately, so peak live memory drops too — one cell churns in place.)

9 · Two heaps, kept in lockstep

wok runs every program twice — once on the abstract IntMap heap, once on the real C arena — and the differential oracle checks the output is bit-for-bit identical and the alloc/free/peak counts match. FBIP must be a shared change so both heaps recycle in the same way and stay in step.

stepabstract heap (IntMap)C arena
a live cell isan index i in stCellsa pointer p
a normal freedelete i, add to stDead, frees++push to freelist[arity], frees++
drop_reuse (rc→0)remove i, not stDead, no frees++; token = idec→0, skip the free list, no frees++; token = p
alloc_at (token)write new cell at i, no allocs++re-stamp header at p, no allocs++
fires whenrc == 1rc == 1

Because both heaps carry the same reference counts at every step, reuse fires on the same cells on both sides. Neither bumps a counter on a fired pair, so both record the same reduced totals — the oracle stays green and the reduction is the visible result.

One honest trade. Today a dangling read on the abstract heap is caught loudly (the index is in stDead). A reused index is live again, so a genuine use-after-free could read the new contents instead of erroring — exactly the masking the C arena already has from its free list. The rc==1 gate guarantees no such reference exists when reuse fires; the malloc-backed ASan build remains the sharp net.

10 · Where the pairing is decided

The runtime just executes drop_reuse / alloc_at. The intelligence — which drop feeds which allocation — lives in the Perceus reference-counting pass, on top of the analysis that already inserts drops and dups. It is a local pattern: a unique boxed cell dropped at a pattern match, with a same-arity allocation it dominates downstream.

11 · How small is the first slice?

Three rungs. The recommendation is the middle one: it delivers the iconic case and forces the token to be a real first-class value, while stopping short of conditional reuse.

S1 · simplest

reverse only

Drop and rebuild are adjacent — the token never crosses a call. Always consumed. Peak drops. But the least iconic demo.

S2 · recommended

map + reverse

Token is held across the recursive call (free in the interpreter — it's just a value). Single path, always consumed. The headline "map → ~0 allocs".

S3 · later

+ filter

A branch drops without rebuilding, so the token needs a "free it for real" path too. Conditional-reuse accounting on top of S2.

fig 11 — deferred beyond the slice: tree insert/balance (cross-constructor, multi-arity), static rc-elision, filter's conditional drop.

The point: the cell that dies and the cell that's born are the same block. The compiler pairs them; the runtime recycles only when the count proves it's safe; both heaps do it identically, so the oracle sees the allocation count fall to zero with the answer unchanged.
