Boxed vs unboxed arrays

How a fixed-size array stores its elements — the wok model, and what Koka (the Perceus reference) actually does. Example element: Vec4 = Vec4 U64 U64 U64 U64 — 32 bytes of payload.

1 · The uniform slot: everything is one word

Every slot is 8 bytes = one machine word. A value is either a scalar that fits in the word (inline, tagged) or a pointer to a heap cell (bigger or polymorphic). One fixed width is what lets a single descriptor + cascade + RC + reuse handle every type.

Koka does the same. Its element/box type kk_box_t is one machine word; the low bit discriminates pointer (LSB 0) from inline value (LSB 1, stored as n*2+1). Small ints, bools, enums sit inline in the word; structs and big integers are pointers. wok uses a 2-bit low tag (00 C-cell / 01 H-addr / 11 immediate) for the same job — same family.

2 · Boxed array — Array Vec4 as pointers

Each slot holds an 8-byte pointer to a separate Vec4 cell (arity 4 → 8 + 4×8 = 40 bytes). The array is N pointers; the structs live in N scattered, individually-refcounted cells.

This is exactly Koka’s vector<a>. The header is kk_box_t vec[] — a contiguous run of boxed words. A vector<Vec4> is N pointers to N heap blocks; Koka does not pack a struct inline into the vector. Even the Perceus reference language stops at boxed-word arrays for the general case.

3 · Unboxed / flat array — Array Vec4 inline

Store the struct inline, contiguously, with a per-element stride of 4 slots (32 bytes). No per-element pointer, no per-element cell, no per-element refcount — one block.

one element = 4 contiguous slots (32B stride) — the Array U64 case is just stride 1

Needs a known, monomorphic element layout; if the struct holds pointers, the array carries a per-element slot-kind vector the cascade applies N times. Best locality, value semantics.

This is how Koka represents string — not as vector<char>. A Koka string (kk_bytes_t) is a flat uint8_t buffer (with a small-string optimization: ≤7 bytes inline in the word), a dedicated unboxed type — precisely because a boxed vector of chars would be wasteful. Strong signal for wok: String wants this flat-bytes flavor, not a boxed Array Char.

4 · The semantic difference (not just layout)

boxed — reference

index shares

  • returns a pointer, bumps the refcount
  • the element is shared with the array
  • elements can be shared across arrays
  • polymorphic: works for any a
flat — value

index copies

  • copies the 32 bytes out (by value)
  • set writes 32 bytes in place
  • no sharing: each array owns its bytes
  • needs a concrete fixed-size element

That is the []*Point vs []Point distinction. wok’s Array a defaults to boxed/reference because a is polymorphic and RC-shared; flat is a specialization you opt into for a concrete element type.

The takeaway: wok’s Slice A/B boxed Array a is the same design as Koka’s vector<a> — uniform boxed words, scalars inline, structs as pointers. The flat/unboxed layout (Slice D) is where a 32-byte struct packs inline, and it’s the representation Koka reserves for string. So when wok eventually builds String (Slice E), the evidence says make it a dedicated flat-bytes type, not a boxed Array Char.
