Array Slice D — unboxed / flat arrays brainstorm

The question is not "how do we pack elements flat?" It is "is there anything to pack, and does it pay now?" This page lays out the central tension, the evidence, and the contested axes — so we can decide together whether to build, re-order, or defer.

A, B, C are all merged (C at 9597c7d, 1409 green, ASan clean). D is highlighted in amber, not blue, on purpose: unlike A–C it has no justifying consumer yet. This brainstorm tests whether D should ship, be re-ordered, or wait for codegen.

0 · The punchline, up front

For the types wok has today, the boxed array IS the flat array. Every scalar wok owns is word-sized (U64, U32 — same rep — Char, Unit, Bool). A scalar element already sits inline in an 8-byte slot — no per-element cell, no pointer. There is literally nothing to unbox. Genuine flat-packing only pays for things wok cannot yet express.

1 · Why scalars are already flat

Slice B gave Array a a real C cell: a 16-byte header then len 8-byte slots. For Array U64, each slot holds the integer directly (a raw KLitInt word, uncounted). That is bit-for-bit what a "flat Array U64" would be. Drawing the two gives the same picture:

The flat-vs-boxed split dissolved in Slice B precisely because there was no second representation to choose.

(b) Sub-word / byte elements — density, mostly codegen-era; really the road to String

Pack N U8/bytes per machine word. The win is cache density + SIMD, which is invisible until there is a native backend (arc §8). The true consumer of flat bytes is not a numeric array — it is String = kk_bytes_t (Slice E). Koka's evidence (§6 below) says strings get their own flat type, not a boxed Array Char.

3 · The YAGNI verdict — does D have a consumer at all?

Anti-over-engineering rule: build only what a real consumer needs. So we swept every .wok program in the repo (430 files). Every single array is either a scalar array (already flat) or a genuinely-boxed array (not flattenable). Zero use a value-struct element.

So the honest framing: Slice D is not "the next optimization" — it is a capability with no caller. That is exactly the situation the arc warned about: D "has no justifying consumer until a value-struct or byte type exists." The brainstorm's real job is choosing among build-foundation-only, re-order the arc, or defer.

4 · The contested axes (directions + a recommendation each)

Axis 1 · What, if anything, justifies flat packing NOW?

direction A

Value-structs measurable

Pack Array (U64,U64) inline. The one win the interpreter can measure today (alloc-count). But needs a struct element type used in an array — which no program has.

direction B

Sub-word / bytes

Density win, but invisible pre-codegen. Its real payoff is String (Slice E), which wants its own flat type, not Array U8.

direction C

Defer / foundation-only lean

No consumer ⇒ don't build representation. At most lay type-system groundwork (a way to say "this element is sized"). Let a real consumer pull the feature.

Axis 2 · Re-order the arc? (D vs String vs regions)

direction A

String (E) is the real flat-bytes consumer argue it

D's sub-word road leads to String. Strings are used everywhere; a flat byte buffer has an immediate, large consumer. Bringing E forward gives flat-bytes a caller D lacks.

direction B

Regions next

Regions are arc-ordered after D but don't depend on it; they pay off on the boxed data we already have (bulk-free, locality). A consumer-rich rung.

direction C

Keep arc order, D as foundation

Build D minimally so later rungs (LoCal serialization needs fixed-size flat elements) have the cell shape ready. Risk: building ahead of need.

Axis 3 · One Array a vs a Sized/unboxed KIND

direction A

Monomorphic-only MVP — no kind lean

Pick a concrete element layout per array; no generic flat-array code, so no need to state "element is sized" in a signature. Sidesteps the kind entirely (the MLton monomorphization precedent — see §6).

direction B

A Sized kind up front

Add KSized to data Kind; constrain Array : Sized -> *. Needed only to write generic flat code (map/fold over any sized element). Real type-system work; the row-kind machinery (KEffect) is the precedent it would follow.

direction C

Per-element typeclass dictionary

A Prim/Unbox-style class carrying the layout, à la Haskell's vector. Avoids a new kind but adds dictionary passing; heavier than wok needs for an MVP.

Axis 4 · Value vs reference semantics of index

This is the one surface-observable difference, and it is subtle.

Boxed index — reference

index returns the element's shared pointer + a dup. Two handles to the same cell. Zero copy.

Flat index — value (materialize)

The bytes live inside the array — there is no cell to point at. index must copy the element out into a fresh value. For a struct element that is a new allocation on every index.

The twist that flips the ledger: flat packing saves allocations at construction but spends one at every materialize-on-index of a struct element. For pure scalars there is no materialize cost (the word IS the value). So flat's net win depends on the access pattern — and the cleanest version (project a single field arr[i].x without materializing the whole struct) is a codegen optimization, not an interpreter one. Worth seeing clearly before committing.

Axis 5 · The C cell + RC + the element layout descriptor

today (Slice B/C)

Stride 1, one elemkind byte

16B header, uniform 8B slots, a single elemkind (the element's SlotKind). Teardown reads that one byte: raw-lit ⇒ O(1); pointer ⇒ cascade.

Slice D needs

Stride > 1 + a slot-kind vector

A struct element spans k slots; a struct with pointer fields ([]Point vs []*Point) needs a per-sub-slot kind map so teardown cascades only the counted fields. The sizeClass rounding Slice B deferred reactivates here.

the saving grace

Teardown cost = element bucket arc §3

All-scalar struct (U64,U64) ⇒ still O(1) teardown, just wider. Only pointer-containing structs cascade. The descriptor is the layout-compaction per-tag-descriptor pattern, generalized to a stride.

Axis 6 · The serialization connection (LoCal endgame)

Flat fixed-size-element arrays ARE the flat unboxed array of LoCal/Gibbon (arc §7) — the first serialization entry point. But the full serialization win is compiled-traversal, codegen-era. Recommendation: pull in none of LoCal now; just note that a stride-based flat cell is the shape a future region/LoCal slice would reuse. Building serialization ahead of a backend would be the textbook over-engineering the arc §8 warns against.

6 · Prior art deep-research · 24/25 claims confirmed

Every value-model / RC / region language that ships flat value arrays tells the same story. The headline: a "Sized"/levity kind is only needed to write generic flat-array code; restricting to concrete element layouts sidesteps it entirely (the MLton existence proof). And the strongest flat-data precedent is not a numeric array at all — it is a dedicated flat byte/String type (Koka).

Koka · the direct precedent

Boxed vector + a SEPARATE flat bytes type

kk_vector_t is strictly an array of boxed words; Koka never generalized it to unboxed elements. Strings are a dedicated flat kk_bytes_t (uint8 buffer + 7-byte small-string optimization), not vector<char>. WHY: bytes have a fixed 1-byte size that doesn't need the runtime's boxed-word uniformity. → flat String, not flat Array.

MLton · the existence proof

Whole-program mono → flat, no kind

Monomorphization yields a simply-typed IL; a Data-Representation/Flatten stage then packs array elements — (int*int) array stores pairs inline, not pointers-to-pairs. No source-level representation kind exists (SML has none). → a monomorphic-only slice sidesteps the Sized/levity kind.

Roc · value-semantics RC

Inline-by-value default

Values are unboxed/inline by default; Box is the expensive opt-in. Because fields are inline (not uniform pointers), reuse analysis must track each variable's specific layout, not just constructor arity. Gated by monomorphization. (The stronger "mono is a prerequisite for reuse" claim was refuted.)

OCaml · the cautionary tale

flat-float-array vs array polymorphism

Uniform one-word rep forces float to be heap-boxed; the flat float array special-case conflicts with 'a array polymorphism (can't statically know if 'a is float) — OCaml 5 changed its default. Reading an unboxed field copies out (materialize-on-read). → don't bolt flat onto the uniform Array a; flat index is value-semantic.

GHC · the kind machinery

Representation lives in the KIND

TYPE :: RuntimeRep -> Type; BoxedRep Lifted vs IntRep… A variable/argument may not be representation-polymorphic (codegen must fix width/pointer/register). Generic flat code uses per-element Prim/Unbox dictionaries instead. → the kind is a generic-code tool, not an MVP need.

Rust/Swift · Gibbon

Sized bound; serialized flat

Rust Vec<T: Sized> stores T inline; Swift value-arrays + copy-on-write. The minimal type-machinery analog is a representable-layout (Sized) bound — unnecessary if you never write generic flat code. Gibbon/LoCal's serialized headerless layout is a compiled-traversal (codegen) win.

the four sub-questionsprior-art answer
(a) Is a Sized/levity kind required?No for an MVP. Needed only for generic separately-compiled flat code. Monomorphic-only sidesteps it (MLton). Minimal analog = a representable-layout bound, and even that is optional.
(b) Value vs reference index?Flat index must copy bytes out (value semantics / materialize-on-read) — OCaml PR #794, confirmed. Boxed returns a shared pointer.
(c) RC teardown of pointer-bearing flat elements?A per-element slot-kind descriptor / scan map (wok's layout-compaction per-tag descriptor, generalized to a stride). No prior-art source specifies it — it would be wok's own contribution.
(d) Worth it in an interpreter?Mostly an alloc-count win that is modest until codegen (where cache/SIMD is the real payoff). No benchmark settles this — design judgment, not a measured datum.

7 · Where this points recommendation

Defer Slice D as a flat value-struct array. It has no consumer in any wok program, its only interpreter-visible win (value-struct alloc-count) is the weakest in the prior art and is unmeasured, and its real payoff (cache/SIMD/serialization) is codegen-era. Building it now is foundation ahead of need — the textbook over-engineering arc §8 warns against.

Re-order: make String = flat bytes (Slice E) the next slice. It is the one flat-data move with (1) a massive real consumer — every string — (2) the strongest precedent (Koka's kk_bytes_t, exactly this shape), (3) an interpreter-visible improvement today (strings are currently non-C abstract-heap values; a flat byte buffer is a real gain now, not just at codegen), and (4) it is a dedicated flat type, which dodges OCaml's polymorphic-array tension entirely. It delivers the "flat" win D promised, on the type that actually needs it.

The decision for you: three live directions — (A) bring String = flat bytes (E) forward as the next slice recommended; (B) pivot to the regions epic (the other consumer-rich rung, on existing boxed data); or (C) a minimal foundation-only D (cell-shape / a representable-layout gate) if you want the groundwork laid before a consumer exists. The evidence leans hard toward (A): a real consumer, the strongest precedent, and a win you can measure now.
