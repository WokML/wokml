Perceus: skipping the tracing GC

What reference counting actually drops, what it keeps, and where the pointer/non-pointer question goes.

One correction first. Perceus skips tracing — yes. But it does not stop "bookkeeping references": the per-object reference count is the bookkeeping. What disappears is the global reachability walk. So allocations aren't metadata-free either — each object still carries a count word — they just carry none of the tracing apparatus (mark bits, card tables, forwarding pointers).

Your questions, directly

tracing GC?

SKIPPED

No graph walk, no mark-and-sweep, no collector pauses.

reference bookkeeping?

KEPT

Each object has a count; the compiler adjusts it inline.

stack maps / safepoint root scan?

NOT NEEDED

There is no GC-time root enumeration to drive.

pointer/non-pointer register split?

NOT (at runtime)

Resolved statically by the compiler instead.

1 · How each one finds garbage

tracing GC

walk from the roots

Pause, start from the roots (stack slots, registers, globals), walk the whole reachable graph, mark what is live, reclaim the rest. To do this it must enumerate roots at runtime.

perceus rc

count, locally

Every object carries a count. Compiler-inserted dup/drop adjust it at use sites; at 0 the object frees itself and decrements its children. No walk, no root scan, no pause.

2 · Where the "is this a pointer?" question goes

The question splits in two — and only one half is what stack maps and register partitioning exist for.

which things are pointers?
↓
roots — stack slots & registers

Tracing: needs maps

A precise trace must know, at every safepoint, which stack/register slots hold live references — that is exactly stack maps + pointer/non-pointer register partitioning.

Perceus: never asked. No root scan → no stack maps, no register partitioning for a collector.

fields — inside an object

Both need this one

To walk (tracing) or to decrement children on free (RC), you must know which fields are pointers.

Perceus: it is the object's static layout, used only when a cell hits 0 (the cascade) — per-type, not a root map.

fig — stack maps and register partitioning answer the roots question; RC never asks it

3 · The cost just moves

tracing pays at

run time

Root scan, stack maps, safepoints, pauses, and write barriers (for generational/incremental variants). The collector is machinery that runs while the program runs.

perceus pays at

compile time

One static analysis decides every dup/drop. At runtime: just inline count bumps and a free when a count reaches 0. Scan-free — no roots, no maps, no pauses.

So the pointer/non-pointer knowledge is not gone — Perceus relies on it. It is just consumed by the compiler (which binders are boxed → where to emit dup/drop) rather than by a collector reading runtime tables. The trade is real: tracing front-loads nothing and pays in runtime metadata + pauses; Perceus front-loads the analysis and runs lean.

The catch. Reference counts can't see cycles — a tracing GC reclaims them for free. wok's price for dropping tracing is guaranteeing no reference cycles by construction (immutable data + the "carrier wall" that keeps a continuation out of the data it owns), instead of bolting on a cycle collector. Two more honest notes: every object still carries a count word, and the inc/dec is real per-operation work (minimized by precise placement and reuse/FBIP); and today wok runs this in an interpreter with an explicit counted Store — the "no stack maps, no register partitioning" payoff is about the eventual compiled backend, which is precisely the model Perceus is designed to enable.
