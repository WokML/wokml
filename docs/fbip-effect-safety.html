FBIP reuse, meet effects & abort

A reuse token is a tiny in-flight reservation. What happens to it when an effect operation captures the continuation it's sitting in — and the handler throws that continuation away?

1 · The token is a reservation held across a gap

FBIP works by reserving a dying cell's shell at drop_reuse and re-stamping it at a later alloc_at. Between those two points the token is in flight — it owns a reserved shell that lives on no list, waiting to be revived. For pure map/reverse the gap is just the recursive call, and the alloc_at always runs.

drop_reuse xsreserve the Cons shell → token born
map f xxrecursive call (the gap)
alloc_at(token)re-stamp the shell → token consumed

fig 1 — the token lives across the gap; in pure code the right end always fires.

2 · An effect op in the gap captures the pending alloc_at

Now put an effect operation in the gap. When op() fires, the machine reifies the continuation — everything still pending, including the not-yet-run alloc_at — into a heap object (an NCont), and hands it to the handler. The in-flight token is now sitting inside that captured continuation.

drop_reuse xstoken born, shell reserved
op()captures the continuation →
pending alloc_at(token) is now inside the NCont
handler decides…resume or abort?

fig 2 — the reserved shell is trapped inside a reified continuation the program no longer controls.

3 · The handler's two choices — and where the shell goes

handler holds the captured continuation
↓
resumethe continuation runs; the pending alloc_at fires and consumes the token. Shell revived. fine
abortthe continuation is thrown away; the alloc_at never runs. Nothing revives or frees the reserved shell. orphaned

fig 3 — resume is safe; abort orphans the reservation.

Two things could go wrong on abort — one already fixed. When the captured continuation is dropped, the runtime walks its frames (continuationOwned) to free what they own. (1) That walk used to hit the RReuseCon and error out → interpreter crash. FIXED — the analysis is now total over RReuseCon (treats its fields like a plain Cons). (2) The reserved shell is owned by the token, which is uncounted, so the walk frees the fields but not the shell → leak. OPEN — this is what we're here to design.

5 · The load-bearing invariant

A reservation never crosses a handler boundary. The pairing already refuses to span a Handle (and now an ROp). So a token's drop_reuse and its alloc_at always sit inside the same handler region. Consequence: at any op, every in-flight reservation is trapped in the continuation being captured right now — there is nowhere else for it to be. That single fact is what makes the cheap fix below correct.

6 · The sweet spot: be lazy, reclaim at abort

The performance question is "does reuse survive a resume?" — because resume is the common case. Eager E (cash out at capture) frees the shell before knowing the handler will resume, so it always loses. The fix is to do nothing at capture and resolve at the fork the NCont already implements:

op captures the continuationdo NOTHING — the reservation rides along, untouched
↓
resumeprefix splices back, the pending alloc_at finds its shell right where it left it → reuses in place (same as B)
abortthe abort path ALREADY walks the prefix to free its owned set; also free the in-flight reuse-token shells it finds → no leak

fig 6 — E+ (lazy reclaim). A reservation can only be orphaned at an abort (§5), so reclaim it there and nowhere else.

7 · Four directions, ranked

E+ · recommended

Lazy reclaim

Do nothing at capture. Resume reuses in place; abort frees the in-flight token shells via the walk it already does.

+ reuse survives a resume (B-level perf)
+ no node kind, no counted token, no C marker, no global set
+ one site: the abort walk
− one targeted special-case at abort

B · the pure version

Counted reserved cell

The shell becomes a counted NReserved placeholder; the token is a counted ref; RC frees it on abort and transfers it on reuse — zero special-casing.

+ RC-uniform, fully principled
− new node + counted token + C-heap "reserved" marker
− most invasive

E · the blunt runtime one

Cash out at capture

Free every reservation the instant a continuation is captured.

+ dead simple
− loses reuse on EVERY capture, even resume

C · static

Effect-gated pairing

Only pair when the spanned calls are provably effect-free (wok has effect rows).

+ no runtime cost
− couples the pass to effect typing; map effectfulF loses reuse

The recommendation: E+ (lazy reclaim). It matches B's performance — reuse survives a resume — at roughly E's cost: no new node kind, no counted token, no C-heap marker. It needs one tiny structure — a stReserved set in the Store (insert at drop_reuse, remove at alloc_at) — so the abort collector can tell an in-flight reservation from a spent token still lingering in an environment. The new code is that set's two hot-path updates, a collector (continuationReservations, a sibling of the existing continuationOwned), and a special-free step in the NCont drop. B stays on the shelf as the "everything-is-RC, zero special-cases" version if we ever want to retire that one special-case at the cost of the C-heap marker.
