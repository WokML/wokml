How a wok String sits in memory — right now

After slice E2 (merged). Short string or long string: same machinery, both live in a heap cell. There is no small-string optimisation yet — that is what E3 is about.

1 · A string value is one 64-bit word — a reference, not the text

Everywhere a string is held (a local, a function argument, a field inside another object) it occupies exactly one machine word. The eight cells below are the eight bytes of that one word — not eight things, one thing. Read together they are a single number. For a string that number is a pointer to a cell elsewhere on the heap; only the lowest 2 bits are carved off as a tag saying what kind of reference it is.

2 · The WokString cell — 16-byte header, then the packed bytes

Every string — including "" and "Hi" — allocates one of these. The header is a fixed 16 bytes (a reference count, a type tag, a byte length); the UTF-8 text follows, padded up to a whole number of 8-byte words.

3 · Small vs long: identical shape today

The only difference between a 2-byte string and a 19-byte string is how many body words follow the header. The small one is almost entirely overhead.

long string

"the quick brown fox" — 19 bytes

cell = 16 + 24 = 40 bytes

fig 3 — same header, same pointer, same allocation; only the body-word count differs

The cost being paid: a 2-byte string spends a 24-byte heap cell, a malloc, and a reference count to carry 2 letters — and even the empty string "" costs a full 16-byte cell. Short strings (single characters, keys, punctuation, "", "/") are common, and right now each one pays the full cell tax.

4 · What E3 would change (the proposal, not current state)

The value word is already 8 bytes and currently just holds a pointer. If a string is short enough, its bytes could live inside that word — no cell, no allocation, no refcount. Long strings keep today's cell. After the 2-bit tag, one word leaves room for about 7 bytes of text; going wider would mean making a string value bigger than one word, which is a separate, much larger change.

5 · What if we used StringZilla's own sz_string_t by value?

StringZilla's container gets 22 inline bytes by making the string value 4 words (32 bytes) wide, stored by value. To get that capacity, a String field could no longer be a one-word pointer — the field itself would have to be a 32-byte struct:

short (≤ 22 bytes)

internal / on-stack

word 0start → points at its own byte 9 (self-referential!)
word 1len (1 byte) + first 7 text bytes
word 2–315 more text bytes + NUL  (22 usable)
long (> 22 bytes)

external / on-heap

word 0start → malloc'd buffer
word 1length
word 2space (capacity)
word 3padding

fig 5 — sz_string_t (header lines 378–414): one 32-byte slot, two interpretations, told apart by whether start points back into itself

Three walls if we adopt it: (1) slot width — wok slots are uniform 8-byte words (uint64 slots[], encodeSlotC yields one word); a 32-byte field makes slots variable-width across the whole machine. (2) self-pointer — an on-stack start points at itself, so the struct can't be memcpy'd; every move must fix it up, yet wok moves values constantly. (3) refcount clash — wok shares strings cheaply by bumping a cell's rc; a by-value struct can't be rc-shared, so long strings would deep-copy on every share or need a refcount bolted back onto the spill buffer (re-introducing the cell). That is a value-model epic, not E3.
The point: today there is no small/long distinction — both are a one-word pointer to a WokString cell (16-byte header + padded bytes). E3 (one word, ~7 bytes inline) is a contained continuation of the existing mechanism. StringZilla's 22-byte SSO is real but only pays off by value at 4× the width — a separate epic that fights wok's uniform slot and its refcount sharing.
