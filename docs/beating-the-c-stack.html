Beating the C stack

wok's allocation isn't one allocator racing the stack. It's a ladder of strategies ordered by the lifetime you can prove — each rung used only where its guarantee holds. The stack is one rung; some rungs sit below it.

2 · How bump allocation works

Memory arrives in big slabs. Allocate = hand back the frontier pointer and nudge it forward. Free = push the cell onto a size-exact LIFO free list (not back to the OS). The next allocate of that size pops the list first (cache-hot), and only bumps when the list is empty.

↑ frontier (bump this forward)

The whole heap tears down in O(number of slabs) — you never walk every object. It runs ~4× faster than malloc because refcounting says exactly when each cell dies, so there is no GC scan, no coalescing, no fragmentation search.

3 · How FBIP reuse works

The refcount pass knows the precise instant a cell's last reference drops. If the next thing the program does is allocate a cell of the same constructor and arity, the dying cell's memory is handed straight over and re-stamped — guarded by a runtime rc == 1 check so it only fires when the cell is truly unique.

below the floor (that one pattern)
The verdict: you don't beat the stack by building a faster allocator — you beat it by not allocating. For non-escaping data the region rung is the stack (and reaches it automatically, memory-safely). FBIP goes below it by recycling. The counted heap is deliberately slower because it does the one thing the stack can't: hold values that outlive their creator. The win is in routing each allocation to the right rung, not in any single rung out-running the others.
